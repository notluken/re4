## `cUnit`/`cCoord`: the rule for a polymorphic base at the root of the object chain

`ID_DATA`'s own +16 was root-caused in docs/port-boot.md section 40 (2026-09-25): it derives from
`cCoord` (`include/model.h:20`), whose own base `cUnit` (`include/cManager.h:38`) is +12 of the +16
by itself, split as:

- `cUnit::pNext` (`cUnit*`, "active list link") -- a plain un-ported native pointer, +4 on host.
  Same shape as every other row in the mismatch table above.
- `cUnit`'s vtable pointer: 4 bytes under the GameCube's GNU v2 ABI (`cUnit` has three virtual
  functions: `~cUnit`, `beginEvent`, `endEvent`), 8 bytes under the host's LP64/Itanium ABI. This
  one is **not** in the mismatch table's "native pointer field(s)" pattern -- it is not a field this
  tree declares at all, so there is nothing to `Ptr32<T>`.
- `cCoord::pParent` (`cCoord*`) adds another +4, same shape as `pNext`.

The remaining +4 of `ID_DATA`'s own +16 was not traced further (plausibly padding shifted by the
above three) -- **TO VERIFY**, not blocking on it: the two `Ptr32<T>` candidates and the vptr
question below are the actual decision this section exists to record.

**The rule, decided this session, for `cUnit`/`cCoord` and by extension every type derived from
them (the entire object chain -- `cEm`/the player, `cObj`, `cLight`, every effect, `docs/
overview.md`):**

- **Plain data pointer fields (`pNext`, `pParent`, and the same pattern in every derived class)
  become `Ptr32<T>` under `TARGET_PC`.** These are exactly the case `Ptr32<T>` exists for: an
  on-disc/relocatable-looking 4-byte handle, safely compressible into the arena window, no
  different in kind from every other row already fixed in the mismatch table above. No new
  decision needed here -- just mechanical work, deferred only for its blast radius (every
  `src/game` file that touches `->pNext`/`->pParent` on any `cUnit`/`cCoord`-derived type, which is
  most of `src/game`), not for any open design question.

- **The vtable pointer does NOT get narrowed, hidden, or worked around.** There is no host
  mechanism that makes a real C++ vtable pointer fit in 4 bytes on an 8-byte-pointer LP64 target
  (a compressed vptr would mean either abandoning real C++ virtual dispatch for these classes, or a
  custom trampoline table -- both are the kind of "invent a hardware mechanism the host doesn't
  have" this project's port rules reserve for actual documented hardware features like GQR/paired-
  single, not for an accident of two ABIs disagreeing on pointer width). `cUnit`/`cCoord` and every
  class deriving from them simply grow by the vptr's extra 4 bytes on host, same as they already
  silently do today (the size mismatch this whole doc measures already includes it).

- **What the vptr growth actually requires, and the reason this has stayed a "needs its own
  session" item rather than a quick fix:** every place in `src/game` that computes, checks, or
  relies on a GameCube-`sizeof()`-shaped budget for one of these types (a pool capacity, a stride
  into an array of them, a raw byte-offset arithmetic past one of them) must use the HOST's
  `sizeof(T)` under `TARGET_PC`, never the GameCube literal, or it silently under/over-allocates
  by exactly the vptr delta. Two sub-cases, already partly proven safe by inspection this session,
  not yet swept for every call site:
  - `cManager<T>`'s own pools (`include/cManager.h`) already allocate `sizeof(T)` per slot via the
    template parameter, not a literal -- host `sizeof(T)` flows through automatically, no call-site
    change needed. This was checked directly (grepped `cManager<T>`'s allocation path) and is why
    this session's own boot-prompt could say "`cManager<T>` pools use `sizeof(T)` -- fine" with
    confidence.
  - Any OTHER literal-byte-count computation involving a `cUnit`/`cCoord`-derived type's size (a
    hardcoded stride, a `memcpy`/`memclr_asm` byte count copied from the PS2 source's own literal,
    a raw pointer-plus-N-bytes walk) is exactly the "GameCube constant vs. host `sizeof()`" question
    the coordinator's own boot-prompt named -- each one needs to be found (grep for the type name
    near `sizeof`/arithmetic, not assumed absent) and switched to `sizeof(T)` under `TARGET_PC`
    specifically, one call site at a time, the same discipline as every other `TARGET_PC` numeric
    lever in this tree. Not swept this session (budget) -- this sweep, plus the `pNext`/`pParent`
    `Ptr32<T>` conversion above, is the cross-cutting work item this doc's own section 40 entry
    already flagged as needing its own session, now with a concrete rule to execute rather than an
    open question.

**Net for `ID_DATA`/the layout-parity report above**: expect `ID_DATA`'s mismatch to drop from +16
to (at most) +4 once the `pNext`/`pParent` `Ptr32<T>` conversion lands, with the vptr's own +4
staying a permanent, correct, documented difference -- `gen_layout_report.py`'s heuristic does not
(and should not) try to special-case it away.

## Struct-view casts: reinterpreting a cUnit/cCoord-chain object as an unrelated, hand-offset type

The same mismatch above (cUnit's vptr is 4 bytes on GC, 8 on this host; cCoord's own `pParent` is
another un-ported +4) has a second consequence, found live this session (2026-09-25) chasing the
`getFloor`/collision and `Trans()`/rendering crashes: any hand-rolled struct that mimics a
cUnit/cCoord-chain member's layout via a **literal absolute GC byte offset** (`u8 pad_0[0xNN]` from
the object's own start, or a raw `(u8*)p + 0xNN` cast) reads the wrong bytes on this host, because
the real object is bigger there than the literal assumes. A struct/macro that instead reaches its
target field through `&realObject->realNamedMember` (an actual, compiler-computed member access,
even if only to reinterpret what comes *after* it) is safe regardless of vptr/pointer width, because
the compiler recomputes the real offset every time. This is the pattern already used successfully by
`MOTION_PARTS`/`IK_PARTS`/`PARTS_BIND_MAT` (`include/motion.h`, prior session) and by
`PEN_WORK` (`src/game/pendulum.cpp`, `(PenParts*) &(p)->pFloor_norm` -- already safe, `pFloor_norm`
is a real `cModel` member, not audited further this pass but confirmed by inspection).

## `cSmd`/SMD table readers: the same "raw table, unswapped" bug as `cSatHeader::getSat`

Found and fixed this session, same root cause and fix shape as the SAT/EAT pass (`atari.cpp`
already had this right for `cSatHeader::getSat`, but the equivalent SMD -- scroll/room-model --
reader was missed): `cSmd::getBinPtr`/`getTplPtr`/`getMotPtr` (`src/game/scroll.cpp`) read their
offset tables through a raw `(u32*) tbl` cast, not `BE<u32>` -- corrupted `SmdSetParam`'s `bin`
pointer, crashing `calcModelAddr` (`(int) d->pClr < 0` dereferencing a garbage `cModelData*`).
`cSmd::slide()` (the same file) has the identical raw-cast shape in its own offset-table walk, but
is gated by a `(u32) w < 0x80000000 || (u32) w > 0x82FFFFFF` GameCube-address-range guard that a
host pointer can never satisfy -- it safely no-ops (logs and returns) before reaching the raw casts,
so it was **not fixed this session** (dead under `TARGET_PC` by construction, not exercised by any
run); flagged here as **TO VERIFY** if a future session changes that guard or the addressing scheme.

## `ModelPart`: another fully-raw on-disc struct, found via the GX FIFO crash it caused

`include/model.h`'s `ModelPart` (the per-part header inside a model BIN's display-list stream,
read by `trans.cpp`/`shadow.cpp`/`mirror.cpp`/`dbmodule.cpp`/`model.cpp`) had **no `TARGET_PC`
branch at all** before this session -- every field, including `size` (the byte length of the
primitive stream `GXCallDisplayList` reads), was raw. Fixed: `size`/`nPoly` (the only multi-byte
fields; the rest are single bytes, no swap needed) are now `BE<u32>` under `TARGET_PC`. Root-caused
live: `GXCallDisplayList(p, part->size)` (`trans.cpp`) handed Aurora's GX FIFO a garbage byte count
(`length=2685075456`), corrupting `aurora::gx::fifo::write_data_grow`'s `memmove`.
